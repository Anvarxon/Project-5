# Отчёт по результатам анализа Kubernetes Audit Log

## Контекст анализа

Выжимка формируется скриптом `filter-audit.sh` из `/var/log/audit.log`, созданного API server с заданной `audit-policy`. Для событий, запускаемых без флага `--as`, инициатором будет пользователь активного административного kubeconfig-контекста (обычно `minikube-user`), а не pod `attacker-pod`: запуск pod сам по себе не меняет идентичность последующих команд `kubectl`.

## Подозрительные события

1. Доступ к секретам:
   - Кто: `system:serviceaccount:secure-ops:monitoring` для команды с `--as`; создание service account выполнил административный пользователь активного контекста.
   - Где: попытка `get` секрета в `kube-system`.
   - Почему подозрительно: service account мониторинга не должен читать учётные данные системного namespace.
   - Оценка: в корректной исходной RBAC-модели запрос должен завершиться `403 Forbidden`; успешный ответ означает уже существующую избыточную привязку либо компрометацию.
   - Ограничение сценария: в современных версиях Kubernetes автоматически созданного секрета `default-token-*` может не быть. Для воспроизводимой проверки следует заранее создать тестовый `Secret` в `kube-system` либо выбрать существующий секрет явно.

2. Привилегированные поды:
   - Кто: административный пользователь активного контекста, поскольку `kubectl apply` не использует `--as`.
   - Что сделал: создал `privileged-pod` с `securityContext.privileged: true` в `secure-ops`.
   - Почему подозрительно: контейнер с такими правами способен влиять на узел и обходить изоляцию контейнеров.
   - Компрометация: успешное создание является критическим нарушением политики; при последующем доступе к host/credentials кластер следует считать скомпрометированным.

3. Использование `kubectl exec` в чужом поде:
   - Кто: административный пользователь активного контекста.
   - Что делал: создал запрос к подресурсу `pods/exec` для pod `coredns` в `kube-system`, выполнив чтение `/etc/resolv.conf`.
   - Почему подозрительно: интерактивное исполнение в системном pod выходит за обычную эксплуатацию приложения и может использоваться для разведки или изменения системного сервиса.

4. Создание `RoleBinding` с правами `cluster-admin`:
   - Кто: административный пользователь активного контекста.
   - Что сделал: связал `monitoring` с `ClusterRole/cluster-admin` через `RoleBinding` в `secure-ops`.
   - К чему привело: `RoleBinding` не даёт кластерные права, несмотря на имя роли, но выдаёт практически неограниченный доступ в namespace `secure-ops`, включая секреты и запуск опасных workloads.
   - Ошибка RBAC: субъект мониторинга может эскалировать действия в своём namespace; создание bindings на привилегированные ClusterRole должно быть запрещено обычным операторам и алертироваться.

5. Удаление `audit-policy.yaml`:
   - Кто: сценарий пытается выполнить команду как `admin`.
   - Возможные последствия при реальном отключении: потеря доказательств инцидента и невозможность обнаружить дальнейшую активность.
   - Важное ограничение симуляции: `kubectl delete -f /etc/kubernetes/audit-policy.yaml` удаляет объект Kubernetes, описанный локальным manifest, а audit policy является файлом конфигурации API server, не API-объектом. Эта команда обычно не удалит файл на control plane и может не породить событие с текстом `audit-policy`. Реальная проверка требует доступа к узлу Minikube и контроля конфигурации API server.

## Ошибки и рекомендации RBAC

| Наблюдение | Риск | Исправление |
| --- | --- | --- |
| Административный контекст используется для прикладных команд и `exec` в `kube-system`. | Компрометация одного credential даёт широкий доступ. | Разделить ежедневные роли и break-glass admin, включить MFA/короткоживущие credentials и аудит. |
| Возможность выдать service account роль `cluster-admin` в namespace. | Эскалация полномочий приложения и чтение секретов namespace. | Запретить `bind/escalate` кроме контролируемой платформенной роли; применять admission policy. |
| PSA/admission не блокирует privileged pod в сценарии. | Побег из контейнера и захват узла. | Включить PodSecurity `restricted` и Gatekeeper-политики из `Task7`. |
| Не выделена отдельная роль чтения audit/secret данных. | Лишнее раскрытие секретов либо отсутствие расследования. | Применить ограниченную, журналируемую роль ИБ из `Task4`, выдаваемую на время расследования. |

## Вывод

Критическими событиями являются успешное создание привилегированного pod, несанкционированный успешный доступ к secret и несанкционированный `exec` в системный pod. Создание указанного `RoleBinding` означает компрометацию namespace `secure-ops`, но само по себе не всего кластера. Сценарий удаления audit policy следует исправить для симуляции воздействия на файл control plane; наличие или отсутствие этого события нельзя считать доказательством без отдельной проверки конфигурации Minikube.
