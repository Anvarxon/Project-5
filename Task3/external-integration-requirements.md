# Требования к внешней интеграции сервисов «Умный дом»

## Решение и границы данных

В мобильном приложении собственника появляются функции интеллектуального домофона и шлагбаума. Внутренний `tenant-core-app` не подключается к партнёру напрямую: все команды и события проходят через новый `Partner Integration Gateway`. Он выполняет авторизацию на уровне объекта, фильтрацию полей, аудит и защиту канала.

PropDevelopment хранит идентификатор собственника, связь с квартирой/ЖК, разрешение на доступ, идентификатор устройства партнёра, статус команды и журнал операции. Изображения лица и биометрические шаблоны не передаются во внутренние CRM/DWH и должны обрабатываться у партнёра в отдельном защищённом контуре. Номер автомобиля передаётся только при наличии цели и согласия, предпочтительно как токенизированный идентификатор разрешения.

## Требования к безопасности

| Область | Требование | Проверка при приёмке |
| --- | --- | --- |
| Минимизация данных | API передаёт только атрибуты, необходимые для выдачи/отзыва допуска и выполнения команды. Биометрические шаблоны и кадры распознавания не импортируются в PropDevelopment. | Анализ OpenAPI/JSON Schema, проверка логов и DWH. |
| Tenant isolation | Каждая операция привязана к `managementCompanyId`, `residentialComplexId`, `deviceId` и праву собственника; партнёр не может читать или менять объекты иной УК. | Негативные IDOR/BOLA тесты и тесты межарендного доступа. |
| Авторизация пользователя | Владелец может управлять только допусками своей квартиры/объекта; высокорисковые действия требуют повторной аутентификации/MFA. | Матрица ролей, интеграционные тесты и audit trace. |
| Защита канала | Только TLS 1.2+; между gateway и партнёром обязателен mTLS с проверкой сертификатов и ротацией. | Конфигурация ingress/egress, тест истечения/отзыва сертификата. |
| Секреты и ключи | Client credentials, сертификаты и ключи хранятся в vault/KMS, не в исходном коде или логах; предусмотрена ротация и аварийный отзыв. | Проверка хранилища секретов и процедуры rotation/revocation. |
| Целостность команд | Команды открытия имеют короткий TTL, nonce/idempotency key и correlation ID; повтор команды не открывает устройство повторно. | Replay/idempotency tests. |
| API hardening | Gateway применяет allow-list схем, валидацию входных данных, rate limiting, timeout/circuit breaker и запрет массовой выгрузки. | DAST/API tests, настройки gateway. |
| Аудит | Неизменяемо журналируются инициатор, основание, объект, scope, команда/событие, результат, партнёр и correlation ID без лишних ПДн. | Поиск событий, контроль доступа к журналам и alert rules. |
| Инциденты | Определены SLA уведомления об утечке/ошибочном открытии, порядок отзыва интеграции и совместного расследования с партнёром. | Договор, runbook, tabletop exercise. |
| Правовые требования | До биометрии фиксируются правовое основание, явное согласие, сроки хранения/удаления, роль оператора ПДн и запрет вторичного использования. | Заключение ИБ/юристов, реестр обработок и договор поручения. |

## Аутентификация и авторизация

| Взаимодействие | Аутентификация | Авторизация |
| --- | --- | --- |
| Мобильное приложение -> backend PropDevelopment | OpenID Connect Authorization Code Flow with PKCE, MFA для настройки допуска и удалённого открытия. | Access token с коротким сроком жизни; серверная проверка роли `owner/resident`, квартиры и разрешённой операции. |
| `tenant-core-app` -> `Partner Integration Gateway` | Workload identity или mTLS между внутренними сервисами. | Scope `smart-access.command`/`smart-access.grant`; запрет обхода gateway сетевыми политиками. |
| Gateway -> API партнёра | OAuth 2.0 Client Credentials с отдельным клиентом на среду и партнёра плюс mTLS. | Узкие scopes (`intercom.open`, `barrier.open`, `access-grant.manage`, `events.read`) и claims с разрешёнными ЖК/устройствами. |
| Партнёр -> Gateway (webhook событий) | mTLS и подписанный webhook (`kid`, timestamp, nonce); отдельный credential для inbound. | Разрешены только зарегистрированные типы событий и устройства соответствующего партнёра. |
| Менеджер УК -> административные операции | Корпоративный OIDC/AD и MFA. | RBAC + привязка к УК/ЖК; выдача биометрического режима только после проверки согласия. |

## Организация взаимодействия

1. Собственник аутентифицируется в приложении и запрашивает добавление допуска либо разовую команду открытия.
2. `tenant-core-app` проверяет связь субъекта с квартирой и передаёт минимальную команду в gateway.
3. Gateway выполняет object-level authorization, добавляет correlation ID, пишет событие аудита и направляет scoped-запрос партнёру по mTLS.
4. Партнёр выполняет распознавание и управление устройствами в своём контуре; в ответ возвращает только результат/событие и внешний идентификатор.
5. Gateway проверяет подпись/сертификат ответа, фильтрует payload, сохраняет audit event и возвращает статус мобильному приложению.
6. События для аналитики передаются только в минимизированной либо обезличенной форме; биометрические данные и секреты исключены из DWH, BI и журналов.

## Контроли эксплуатации

| Контроль | Реализация |
| --- | --- |
| Разделение сред | Раздельные credentials и endpoints для dev/test/prod; production-ПДн не используются в тесте. |
| Мониторинг | Алерты на межарендные отказы, массовые команды, аномальное открытие, ошибки подписи webhook и изменения scopes. |
| Доступ партнёра | Onboarding с security review, договорными ограничениями и реестром API; offboarding отзывает сертификаты и tokens. |
| Отказоустойчивость | Ошибка партнёра не снимает физические меры доступа; circuit breaker и явное отображение отказа пользователю. |
| Изменения | Изменение схемы API, полей ПДн или способа распознавания проходит согласование специалистом ИБ и владельцем данных. |
